# 遵守—打破—建立规则

## R — 原文（Reading）

> 这就是游戏三阶段，遵守规则，打破规则，建立规则。
>
> — 碧树西风，BXSF-077 · 2024-09-20

> 你必须先建立规则，规则不等于完善，能够长期稳定盈利的交易系统，也许最初建立出来之后，是稳定亏损的。
>
> — 碧树西风，BXSF-016 · 2022-07-01

## I — 方法论骨架（Interpretation）

1. 第一阶段在既定规则内获得基本能力、信用和反馈，避免连游戏都没玩懂就批判游戏。
2. 第二阶段识别规则的边界、可改参数和真正评价函数；打破只指合法改变结构，不指违规。
3. 第三阶段把经验固化为自己的流程、产品、标准、渠道或交易系统，使结果可重复。
4. 建立规则意味着承担结果和治理责任，而不是把成本转嫁给别人。

## A1 — 语料中的应用（Past Application）

### 案例 1：从技术竞赛转向生态和标准

- **问题**：作者自述进入甲方后发现技术优胜不等于产业胜出。
- **方法论的使用**：从规则接受者转向观察市场整合、标准和生态控制。
- **结果与证据边界**：认知转折为作者自述。
### 案例 2：顺上市阶段重构软件规则

- **问题**：作者推动平台化架构并重组团队。
- **方法论的使用**：不再只做局部代码，而是改变复用、成本和组织评价规则。
- **结果与证据边界**：结果与原因来自作者单方复盘。

## A2 — 触发场景（Future Trigger）

### 用户会在什么情境下需要这个 skill？

1. 长期被平台评分或低价竞争锁住
2. 执行能力强却进不了管理/产品角色
3. 需要把个人经验变成系统
4. 现有评价规则与目标错位

### 语言信号

- “我把规则里的每项都做满了，为什么还上不去”
- “怎样摆脱平台抽成”
- “怎么从接任务变成做产品”
- “我需要建立自己的 rule”

### 与相邻 skill 的区分

- 与 `role-incentive-hidden-information-audit` 的区别：改规则前要理解当前参与者、激励和权限。
- 与 `bottleneck-time-allocation` 的区别：规则建立后，用瓶颈 skill 识别当前最值得改变的参数。

## E — 可执行步骤（Execution）

1. **还原现有规则**
   - 完成标准：写出参与资格、评价函数、资源分配、违规线和退出成本。
   - 判停/转向：不能解释规则如何产生结果时先继续学习。
2. **完成规则内生存**
   - 完成标准：证明能稳定交付并获得反馈，不把基本功不足误判成规则压迫。
   - 判停/转向：未达最低生存线时暂不进入破局。
3. **找可改参数**
   - 完成标准：区分固定法律/伦理边界与可谈流程、定价、渠道、产品和角色。
   - 判停/转向：任何越权或欺骗方案立即删除。
4. **设计最小新规则**
   - 完成标准：把一个重复问题固化成流程、产品、标准或直接关系，并定义谁获益、谁承担成本。
   - 判停/转向：无法承担结果时不发布。
5. **验证治理**
   - 完成标准：检查新规则是否可重复、可退出、可申诉且没有隐性转嫁伤害。
   - 判停/转向：治理失败则退回规则内阶段。

### 边界路由规则

- 用户尚未掌握基本规则却想制定行业标准时，仍由本 skill 触发阶段诊断；结论必须是停在‘遵守规则’阶段，先完成可验收交付和反馈，而不是直接设计新标准。

## B — 边界（Boundary）

### 不要在以下情况使用

- 违法、作弊、侵权或操纵他人
- 基本规则尚未掌握时不得进入打破/建立阶段，但应先做阶段诊断
- 只为获得控制感而增加无用流程

### 作者在语料中警告的失败模式

- 训练方式与目标角色错位
- 把考勤控制当经营
- 因一次结果临时改规则
- 洞察问题却不创造可用结果

### 作者盲点与证据局限

- ‘打破规则’措辞易被误读，必须受法律、伦理和授权约束
- 并非每个人都有制定外部规则的权限，但仍可建立自己的工作系统

### 统一安全边界

- 这是从公开文章中提炼的方法，不代表作者本人对新问题的真实意见。
- 不复制作者亲历，不冒充作者，不把自述案例当作独立核验事实。
- 涉及时效事实、法律、医疗或财务高风险问题时，先获取当前可靠资料并明确不确定性。
