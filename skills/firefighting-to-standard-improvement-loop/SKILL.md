# 救火转标准化改进闭环

## I — 方法论骨架 (Interpretation)

反复救火不是因为大家不知道要解决问题，而是因为每次只处理了表面事件，没有把问题变成可测、可验证、可固化的流程改进。
这个方法把 PDCA 改写成一条管理闭环：先用数据描述现状和主要问题，再找出主因，设定目标和 5W1H 对策。
执行时不能只靠口头要求，要保留过程记录和原始数据。
检查时对照目标判断对策是否有效；无效就回到方案选择，而不是继续喊口号。
有效的对策也不能马上全量制度化，高影响流程需要复测后再写进 SOP。
最后把成功经验标准化，把遗留问题放入下一轮循环。
第十五批 8D 资料补强了这条闭环的事故处理顺序：临时措施只负责遏制影响，不能当作解决；永久纠正必须指向已验证根因和漏检点；防再发要进入标准、培训、点检、系统规则或复查机制。
它的核心是把"这次赶紧补上"转成"下次系统不会再这样掉链子"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 危急值漏报率改进

- **问题**: PPT 在处理阶段举到"危急值漏报率降低至 5%"，完成一轮循环后检查发现没有达到目标。
- **方法论的使用**: 不把第一次方案视为完成，而是总结经验，进入第二轮 PDCA，按计划重新实施。
- **结论**: 未达标不是简单责备执行人，而是把未解决问题放入下一轮。
- **结果**: 第二轮按计划重新实施后达到目标值。

### 案例 2: 救火式处理转持续改进

- **问题**: CQI 段落把"出现问题、解决问题"定义为偶发性、无计划性的救火式改进。
- **方法论的使用**: 转向对现有过程进行渐进、稳定、有计划的改进。
- **结论**: 流程问题需要过程管理和环节控制，而不是只追求一次性技术革新。
- **结果**: 改进目标从维持原绩效水平，转为持续提升满足服务对象需求的能力。

### 案例 3: 8D 从补救到防再发

- **问题**: 8D 资料把问题处理拆成团队、问题描述、临时措施、根因验证、永久纠正、执行验证、防再发和团队复盘。
- **方法论的使用**: 先用临时措施遏制影响，再验证根因与忽略点，最后确认永久纠正并防止再现。
- **结论**: “客户已补偿”“这次已修好”都不是闭环完成。
- **结果**: 方案必须留下验证证据、标准化动作和复查日期。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 客服漏回、内容错发、交付延期、数据漏填、质检不稳等问题反复出现。
2. 领导已经开始要求"大家以后注意"，但没有现状数据、主因和标准化动作。
3. 团队做过补救动作，却不知道是否真的降低复发率。
4. 已有 SOP，但执行记录和效果检查断裂，导致标准变成墙上文件。
5. 一次改进有效，用户想把它推广到更多团队或流程。
6. 已经做了临时补偿、人工兜底或紧急修复，但担心同类问题下月复发。

### 语言信号

- "又出同样的问题了"
- "别再救火了，怎么固化成 SOP"
- "用 PDCA 帮我改这个流程"
- "这个质量问题老复发"
- "8D / temporary containment / permanent corrective action"
- "临时措施和永久措施怎么分?"
- "continuous improvement / process improvement / standardize this"

### 与相邻 skill 的区分

- 与 `okr-fit-preflight` 的区别: 本 skill 处理 1-N 稳定流程的持续改进；OKR 预检判断是否应把目标管理机制用于 0-1 探索和组织对齐。
- 与 `issue-hypothesis-logic-tree-loop` 的区别: 本 skill 默认问题属于可测的稳定流程；如果原因空间复杂、议题不清或要先验证关键假设，转逻辑树。
- 与 `fishbone-major-cause-verification-workshop` 的区别: 鱼骨/5Why 负责找主要因和漏检点；本 skill 负责临时遏制、永久纠正、执行验证和防再发。
- 与 `task-brief-5min-start-loop` 的区别: 任务澄清适合单次任务入口；本 skill 负责让反复问题完成改进循环并固化标准。

## E — 可执行步骤 (Execution)

1. **确认是否是稳定流程复发问题**
   - 列出问题、发生频率、影响对象、最近 3-5 次样本和当前补救方式。
   - 完成标准: 能说明"这是同一类流程问题"，而不是一次性事故或探索性难题。
   - 判停条件: 如果目标本身不确定或要探索新方向，先转 `okr-fit-preflight` 或 `issue-hypothesis-logic-tree-loop`。

2. **用数据描述现状并选主要问题**
   - 写出基线指标、时间范围、影响规模、可观测事实和当前目标。
   - 完成标准: 至少有一个可复查指标或样本口径；不能只写"大家感觉很乱"。

3. **先做临时遏制**
   - 写清短期止血动作、适用范围、负责人、截止时间和退出条件。
   - 完成标准: 影响被控制，且所有人知道这不是永久解决方案。
   - 判停条件: 仍在造成重大客户、安全、合规或财务损失时，先升级应急处置。

4. **找根因、漏检点和主因**
   - 收集可能原因，按人、方法、工具、材料、环境、规则或流程节点分组。
   - 完成标准: 标出 1-3 个最主要、最直接、最可控的因素，并说明证据；同时写出为什么没有被及时发现或阻止。
   - 停止条件: 如果主因无法用现有证据区分，先设计小调查或样本抽查，不直接定方案。

5. **制定永久纠正措施**
   - 写清 Why、What、Where、Who、When、How，并附目标指标、资源约束和风险预案。
   - 完成标准: 每条永久措施都对应一个已验证根因或漏检点，有负责人、时间、执行位置、验收口径和记录方式。

6. **执行并验证**
   - 按计划执行，记录偏差、异常、原始数据和现场反馈。
   - 完成标准: 后续能追溯"做了什么、谁做的、何时做的、结果是什么"，并能判断永久措施是否真的降低复发。
   - 判停条件: 出现安全、合规、客户重大损失风险时，先升级处置，不等完整周期。

7. **检查效果并决定下一轮**
   - 对照目标比较改进前后数据，判断方案有效、无效或证据不足。
   - 完成标准: 输出继续、调整、停止或进入下一轮 PDCA 的明确判断。

8. **标准化、防再发和复盘**
   - 对证明有效的做法写入 SOP、清单、模板、系统规则、培训、点检或防错机制；把未解决问题列入下一轮。
   - 完成标准: 有标准文件、培训/通知对象、复查日期、遗留问题清单和防再发责任人。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 目标是创造新业务、新产品、新增长路径，而不是稳定流程改进。
- 只是个人单次失误复盘，应优先使用个人复盘或错误学习类 Skill。
- 事实、权限、资源、责任边界完全不清，先做问题定义或任务澄清。
- 医疗、法律、安全、财务重大风险场景，本 skill 只能辅助流程复盘，不替代专业合规判断。
- 根因尚未验证，只凭猜测就想标准化，应先转 `fishbone-major-cause-verification-workshop`。

### 资料中警告的失败模式

- 没有用数据说明现状，导致问题被情绪化定义。
- 只找原因，不区分主因和次因。
- 执行阶段不做过程测量和原始记录，检查阶段无法判断方案是否有效。
- 一次有效就仓促改标准，高影响制度没有经过多次循环验证。
- 救火式处理只把结果维持在原绩效水平，没有形成稳定、有计划的改进。
- 把 D3 临时措施当 D5/D6 永久纠正，导致问题反复发生。
- 只修发生原因，不修漏检点和系统漏洞。

### 来源局限

- 本来源是培训 PPT，未标注作者，证据强度弱于专著或真实项目报告。
- PPT 偏质量管理语境；迁移到内容、创业、客服等场景时，要重新定义指标和样本。

### 复盘方式

- 复查新 SOP 是否降低复发率，而不是只检查有没有写文件。
- 记录本轮主因判断是否准确；如果无效，说明哪些原因被漏掉。
- 每轮结束保留"有效措施、无效措施、遗留问题、下一轮日期"四项。
- 复查临时措施是否按退出条件撤掉；如果临时兜底长期存在，要重新评估永久纠正是否失败。
