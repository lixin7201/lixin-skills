# R1/R2 问题界定与诊断逻辑树

## R — 原文 (Reading)

> 展开问题的各要素：切入点/序幕、困扰/困惑、现状R1、目标R2、答案、疑问。
>
> — 芭芭拉·明托，《金字塔原理》第8章

> 问题是指现状与预期状况之间存在差距，并已形成不利或潜在不利，必须加以解决。
>
> — 《“碎石法”问题分析与解决》转换文本 lines 64-72

> 从用户的角度、从现象角度描述问题，不能将原因、解决方法作为问题。
>
> — 《“碎石法”问题分析与解决》转换文本 lines 336-343

## I — 方法论骨架 (Interpretation)

解决问题前，先确认你到底在解决哪个差距。
R1 是当前不满意的结果，R2 是期望达到的结果；问题不是现象本身，而是 R1 到 R2 之间的差距和必须回答的疑问。
第十五批问题解决资料把这个规则说得更操作化：问题陈述必须从用户和现象角度写，不能把原因、解决办法、主观判断或否定句混进去。否则后面的 5Why、鱼骨图、8D 或逻辑树都会沿着错误入口展开。
界定清楚后，再区分两类结构：找原因用诊断框架，找方案用逻辑树。
诊断框架帮助提出可能原因和验证假设；逻辑树帮助展开可选方案和影响。
如果 R2 模糊，就不要急着比较方案，因为优劣没有评判标准。

## A1 — 书中的应用 (Past Application)

### 案例 1: 家庭用品零售商仓储战略
- **问题**: 现有配送中心已经紧张，公司还计划开新店，需要在多种仓储方案中选择。
- **方法论的使用**: 先写出现状、目标、约束和疑问，再把问题转成“选择哪个方案”。
- **结论**: 多方案决策要先定义 R1/R2 和评判标准。
- **结果**: 方案比较从优缺点罗列变成目标约束下的选择。

### 案例 2: 美国电话公司软件出海建议书
- **问题**: 客户想把软件卖到发展中国家，但不知道市场如何细分、哪些市场有吸引力。
- **方法论的使用**: 咨询建议书先复述客户处境和疑问，再说明分析方法和聘用理由。
- **结论**: 提案要先证明理解客户问题。
- **结果**: 服务模块被放回客户决策问题之下。

### 案例 3: 期间图表账流程改造
- **问题**: 多部门数据录入和私改图表造成错误，没人对图表可靠性负责。
- **方法论的使用**: 画旧流程和新系统，定位录入、计算、改动三类错误，再提出三项改变。
- **结论**: 恰当描述问题后，解决方案常隐含在流程差异里。
- **结果**: 流程类备忘录围绕关键错误和控制点展开。

### 案例 4: “碎石法”的问题陈述门
- **问题**: 资料把“问题”定义为现状与预期之间的差距，并警告不能把原因和解决方法写成问题。
- **方法论的使用**: 先写现状、目标和差距，再用谁、何时、何地、什么程度等信息把问题具体化。
- **结论**: “客服质量差，所以要换系统”不是合格问题；“6月夜班客服首次响应从目标3分钟变成8分钟，影响新客咨询”才是可分析问题。
- **结果**: 后续根因分析从方案争论退回到事实入口。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 团队直接争论“做投放还是改产品”“选 A 还是 B”，但目标状态不清。
2. 复盘或诊断里现象、原因、方案混在一起。
3. 用户要求做根因分析、咨询提案、运营诊断、流程改造或策略选择。
4. 数据很多但不知道该收集什么证据、验证什么假设。
5. 问题陈述里出现“因为、所以、应该、换系统、员工不行”等原因、方案或主观词。

### 语言信号

- “我们到底在解决什么问题”
- “先别急着给方案，帮我定义问题”
- “R1/R2”
- “root cause / diagnostic framework / logic tree”
- “这些方案怎么选”
- “这个问题描述合格吗？”
- “是不是把原因/方案写进问题里了？”

### 与相邻 skill 的区分

- 与 `conclusion-first-pyramid-report` 的区别: 本 skill 先把真实问题界定清楚；结论先行用于把已经想清的问题和答案表达清楚。
- 与 `scqa-reader-question-introduction` 的区别: R1/R2 用于分析和诊断；SCQA 用于把已界定问题写成读者会进入的序言。
- 与 `problem-analysis-tool-router` 的区别: 路由器决定该用哪类方法；本 skill 只负责把问题入口写到可分析状态。
- 与 `horizontal-grouping-logic-check` 的区别: 本 skill 处理问题和方案的因果/目标结构；横向检查处理文字要点分组。

## E — 可执行步骤 (Execution)

1. **写问题序幕**
   - 描述问题发生的业务领域、对象、时间范围和稳定状态。
   - 完成标准: 读者知道问题在哪个系统里发生。

2. **标出困扰或变化**
   - 写清打破稳定状态的事件、约束、异常或机会。
   - 完成标准: 困扰能解释为什么现在必须处理。

3. **定义 R1 与 R2**
   - R1 写当前不满意结果；R2 写期望结果，二者必须是同一维度。
   - 完成标准: 可以比较 R1 与 R2 的差距。
   - 判停条件: R2 只能模糊描述时，先对齐目标和约束，不进入方案比较。

4. **清洗问题陈述**
   - 删除原因、方案、主观词、人格判断和无法观察的形容词。
   - 完成标准: 问题只描述对象、范围、当前状态、目标状态、差距和证据来源。
   - 判停条件: 如果用户拒绝把方案假设降级为待验证判断，不进入根因或方案分析。

5. **形成主要疑问**
   - 把差距转成必须回答的问题，如“为什么下降”“如何达到”“选哪个方案”。
   - 完成标准: 疑问能直接决定下一步分析任务。

6. **选择诊断框架或逻辑树**
   - 找原因时用诊断框架列可能原因；找方案时用逻辑树展开可选行动。
   - 完成标准: 每个分支都服务于 R1 到 R2 的改变。

7. **设计证据验证**
   - 为每个假设写需要什么证据、如何证明或排除。
   - 完成标准: 没有“顺便收集”的资料；每项资料都对应一个假设。

8. **产出问题定义卡**
   - 输出 S/C/R1/R2/Q、诊断框架或逻辑树、证据清单、暂定结论。
   - 完成标准: 团队能据此决定先查什么、暂缓什么。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 任务只是改写报告、写开头或检查幻灯片，不涉及真实问题诊断。
- 目标、利益相关方和约束无法获取，强行界定会制造伪问题。
- 已有清晰问题和验证路径，只需要执行，不需要重新拆解。
- 已经明确要开鱼骨图或 8D 纠正会，且问题陈述已合格，应转下游根因或改进 Skill。

### 作者在书中警告的失败模式

- R2 模糊时假装比较备选方案。
- 原因没证实就列行动清单。
- 用资料收集代替假设验证。
- 把“原因”“解决方法”直接写进问题，导致后续分析只是在证明既有偏见。

### 作者的盲点 / 时代局限

- 诊断框架需要领域知识；缺少业务上下文时，结构会漂亮但空泛。
- 该体系对组织政治、利益冲突和价值判断讨论不足，复杂决策不能只靠逻辑树。

### 复盘方式

- 回看最终方案是否真的能把 R1 推向 R2；不能解释的方案应删除。
- 检查每项证据是否验证了一个明确假设；无假设的数据收集应停止。
- 回看原始问题陈述中被删除的原因/方案，哪些后来被证实，哪些只是早期偏见。
