# 议题-假设-逻辑树验证闭环

## R — 原文 (Reading)

> "借助逻辑树发现问题的构造之后，接下来就要明确争论点：'什么是关键的问题？'明确争论点，也就是提出假说。"
>
> — 大岛祥誉，《麦肯锡工作法》第2课

> 一个主导性的问题或坚定的假设；具体，不笼统。
>
> — 《麦肯锡方法论：发现和分析问题的七个步骤》转换文本 lines 68-76

> 记住假设也是会被推翻。
>
> — 《麦肯锡方法论：发现和分析问题的七个步骤》转换文本 lines 404-428

## I — 方法论骨架 (Interpretation)

复杂问题不要从方案开始，也不要把所有可能原因平均用力排查。
先把现象改写成一个值得回答的议题。
再用逻辑树把大问题拆成相互区分、尽量不重不漏的小问题。
拆完以后，不是继续无限展开，而是挑出最可能影响结果、最值得争论的关键点，写成假设。
假设只是临时答案，必须降级为待验证判断。
最后用要点树或证据清单逐项验证：什么证据能支持它，什么证据会推翻它，验证通过后才进入方案设计。
第十五批麦肯锡七步资料把这个闭环补成一个工作流：先写主导问题或坚定假设，再选择推论树、以假设为主的逻辑树或问题图；从逻辑树叶节点生成工作计划；分析时反复在假设和数据之间来回，达到够精确即可停止。
这个闭环的价值是把"大家觉得"转成"我们先验证哪一个关键判断"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 营业员业绩上不去
- **问题**: 只知道业绩总是上不去，但不知道真正原因。
- **方法论的使用**: 作者用逻辑树把问题拆成新顾客、顾客购买量等分支，先俯瞰问题构造，再判断哪个分支可能是真正问题。
- **结论**: 不能把"销售不努力"这类感受当结论，要先把原因结构化。
- **结果**: 问题从笼统抱怨变成可验证的原因分支。

### 案例 2: 汽车制造商发展战略
- **问题**: 汽车制造商要制定发展战略，但利润下降的真正要点不清。
- **方法论的使用**: 先用逻辑树结构化，再把"每台汽车收益率下降"设为关键假设，并用升级版车型试驾促销等要点树验证。
- **结论**: 关键假设成立时，后续行动才有方向；若不成立，应回到问题树重选要点。
- **结果**: 分析从全量散查转为围绕高影响假设的验证。

### 案例 3: 麦肯锡七步的工作计划
- **问题**: 复杂研究容易等数据收集完才开始，或在非关键问题上过度分析。
- **方法论的使用**: 从逻辑树叶节点开始，为每个重要议题写假设、分析、资料来源、方法、负责人和时间安排。
- **结论**: 工作计划不是行政排期，而是把假设验证落到证据和责任人。
- **结果**: 团队能随着数据反复修订假设，而不是被原计划绑死。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 团队已经在争论方案，但没人能说清真正议题和关键假设。
2. 用户要做增长、降本、转化、组织协作、产品迭代或创业判断，原因链条很多。
3. 现象被某个直觉解释绑架了，例如"销售不努力""价格太高""用户没需求"。
4. 用户想知道先查什么数据、先验证哪个方向、哪些分析可以暂缓。
5. 复盘里行动清单很多，但没有证据证明哪个动作能改变结果。
6. 用户想按麦肯锡七步写主导问题、逻辑树、工作计划和关键分析。

### 语言信号

- "先验证什么"

- "这是根因吗，还是假设?"
- "别直接给方案，先拆问题"
- "hypothesis-driven / key issue / root cause"
- "主导性问题 / 问题图 / 叶节点工作计划"
- "够精确即可，不要完美主义分析"

### 与相邻 skill 的区分

- 与 `problem-definition-r1-r2-diagnostic-tree` 的区别: 先用 R1/R2 界定现状、目标和主要疑问；本 skill 接在问题初步可描述之后，把议题推进到逻辑树、假设和验证。
- 与 `primary-source-fact-grounding` 的区别: 本 skill 负责生成和筛选假设；后者负责为假设寻找原始材料、一手事实和证据边界。
- 与 `sky-rain-umbrella-action-chain` 的区别: 本 skill 处理多分支复杂问题；空雨伞处理事实已经出现但意义和行动断裂的短链路。
- 与 `problem-analysis-tool-router` 的区别: 路由器判断是否该用麦肯锡七步；本 skill 只在确认需要假设和逻辑树迭代时运行。

## E — 可执行步骤 (Execution)

1. **把现象改写成议题**
   - 写出当前现象、影响对象、时间范围和要回答的问题。
   - 完成标准: 议题能以一句疑问句表达，并且回答后会改变行动。
   - 判停条件: 如果 R1/R2、目标或决策权不清，先调用 `problem-definition-r1-r2-diagnostic-tree`。

2. **选择逻辑树类型**
   - 在推论树、以假设为主的逻辑树、问题图中选一种；按可能原因、影响环节或方案路径拆出 3-7 个一级分支。
   - 完成标准: 树型与任务一致，一级分支尽量不重不漏，并覆盖主要解释空间。

3. **继续拆到可验证层**
   - 对每个重要分支继续拆小问题，直到能对应一个可观察证据。
   - 完成标准: 每个叶子节点能写出"如果它是真的，我会看到什么"，并能用是/否或明确阈值回答。
   - 停止条件: 分支影响小、不可行动或验证成本高于决策价值时停止展开。

4. **提出关键假设**
   - 选出 1-3 个最可能影响结果、最有争议、最可验证的节点。
   - 完成标准: 每个假设都能被证据支持或推翻，且不是价值判断；写明被推翻后的备选分支。

5. **从叶节点制定工作计划**
   - 为每个关键叶节点列出假设、分析动作、资料来源、分析方法、负责人、截止时间和推翻信号。
   - 完成标准: 团队知道先查什么、不查什么、谁负责、何时回到逻辑树重选假设。

6. **进行关键分析并迭代**
   - 在假设和数据之间来回修正，优先分析最重要、最快推翻或支持判断的证据。
   - 完成标准: 每个关键假设被支持、修正或推翻；非关键问题有明确暂缓理由。
   - 停止条件: 已达到足以改变行动的精度，不继续追求完美数据。

7. **输出决策推进表**
   - 输出议题、逻辑树、关键假设、工作计划、验证结果、暂定结论、下一步。
   - 完成标准: 方案建议只基于已验证或明确标注为待验证的假设。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 用户只是要润色文本、写标题、整理 PPT 页面或做表达结构。
- 事实已经很简单，只缺"所以怎样/怎么办"的一步推理，优先 `sky-rain-umbrella-action-chain`。
- 问题目标、利益相关方、权限或 R1/R2 完全不清，先做问题定义。
- 法律、医疗、投资、安全事故等高风险判断，不能用本 skill 替代专业意见。

### 作者在书中警告的失败模式

- 逻辑树分解时遗漏或重叠，导致解决方案效果变弱并返工。
- 受感情、强势意见或声音大小干扰，没有根据事实基础分解问题。
- 对所有分支平均分析，耗时无限延长。
- 假设写成不可推翻的立场或口号。
- 等所有数据收集完才开始分析，错过早期修正假设的机会。
- 追求完美精确，超过决策所需仍继续钻细节。

### 作者的盲点 / 时代局限

- 书中默认咨询式项目拥有较高信息权限；普通组织中可能缺数据、缺授权或受政治因素影响。
- 假设驱动容易被误用成过早定论，所以必须把假设写成可证伪的临时判断。
- 麦肯锡资料默认有项目组和专家资源；个人创业或小团队使用时，要把工作计划缩小到能获得的数据和验证动作。

### 复盘方式

- 回看最初选出的 1-3 个假设是否真的解释了结果变化。
- 检查被放弃的分支是否因低影响或高成本被合理停止，而不是被偏见忽略。
- 记录哪类证据最快推翻错误假设，下次优先使用。
- 复盘每个叶节点工作计划是否真的推动了结论，删除只增加工作量的分析项。
