# 沟通理解执行闭环

## R — 原文 (Reading)

> 当一个人心里想的是100%的信息或观点，当他试图用语言表达出来时，可能只能表达出80%的内容。
>
> — 《分章节P2-03 沟通能力》Slide 9, lines 67-69

> 复述回答，复述对方的回答让对方知道你懂了；总结整个对话，确保对话达成共识。
>
> — 《分章节P2-03 沟通能力》Slide 26, lines 252-267

## I — 方法论骨架 (Interpretation)

沟通失败常常不是“我有没有说”，而是信息从想法、表达、理解到执行的每层都在损耗。这个 skill 把沟通从一次性输出改成闭环：表达前明确希望对方理解和执行什么；表达时区分事实、解读、感受、请求；表达后让对方复述任务、资源、时间和验收标准。

它吸收 FIRE、SCRTV、ADISC/OELS、OFNR 和 LEAPS，但不把它们拆成多个重复 skill。核心是减少误解，确认共识，并把共识落到执行动作。

## A1 — 书中的应用 (Past Application)

### 案例 1: 沟通漏斗

- **问题**: 想法到表达、理解、执行逐层缩水。
- **方法论的使用**: PPT 用 100%-80%-60%-20% 描述损耗，提示必须关注执行端是否真的接收到。
- **结论**: 不能只检查自己说没说，还要检查对方理解和执行。
- **结果**: 沟通从“发出信息”变成“达成共识”。

### 案例 2: 非暴力沟通与 LEAPS

- **问题**: 对方迟到等冲突容易从事实滑向评价。
- **方法论的使用**: 用观察、感受、需要、请求区分事实与想法，再用倾听、换位、询问、复述、总结确认。
- **结论**: 先清事实和需求，再谈请求和共识。
- **结果**: 降低误解和命令式沟通。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 用户说“我已经讲了，但对方还是按自己的理解做”。
2. 任务、反馈、冲突或方案沟通后，对方执行结果偏离。
3. 双方争论时混淆事实、解释、感受、需求和请求。
4. 用户需要把沟通结果转成可验收的行动闭环。

### 语言信号

- “我讲了三遍他还是没懂”
- “帮我确认对方理解没有偏差”
- “这段沟通怎么说才不会误解”
- “communication loop / paraphrase / execution alignment”

### 与相邻 skill 的区分

- 与 `accurate-restatement-feedback-loop` 的区别: 该 skill 偏单次复述与反馈；本 skill 覆盖表达、理解、请求和执行验收整条链。
- 与 `delegation-readiness-leadership-style-check` 的区别: 本 skill 解决沟通损耗；授权 skill 解决能力/承诺和领导方式匹配。

## E — 可执行步骤 (Execution)

1. **定义执行结果**
   - 完成标准: 写清希望对方理解什么、做什么、何时完成、如何验收。

2. **拆事实与解释**
   - 完成标准: 用 FIRE/OFNR 区分事实、解读、感受、需要、请求，删除人格评价。

3. **组织表达**
   - 完成标准: 根据场景用简短结论、SCRTV 或请求句表达；保留关键依据和边界。

4. **让对方复述**
   - 完成标准: 对方能复述目标、动作、资源、时间、风险和验收标准。
   - 判停条件: 对方复述不一致时，不进入执行，回到事实和请求重述。

5. **设置回看点**
   - 完成标准: 明确一次检查时间、反馈方式和偏差处理机制。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 对方故意违规、骚扰、欺诈或涉及权力伤害，需要正式程序和留痕。
- 用户要求用沟通技巧操控、隐瞒风险或剥夺对方拒绝权。
- 问题根源是资源不足、目标错误或权限缺失，应转任务/授权/组织问题。

### 作者在书中警告的失败模式

- 只说自己想说的，没有检查对方理解。
- 把观察写成评论，把请求写成命令。
- 只追求 30 秒表达，遗漏必要依据和风险。

### 作者的盲点 / 时代局限

- PPT 汇集多个沟通模型，但对权力不对等和合规流程强调不足；正式使用时高风险场景必须升级。

### 容易混淆的邻近方法论

- SCRTV 是表达链，不保证对方理解和执行；本 skill 要求复述与验收。
- 反馈模型不是授权模型；能力不足或承诺不足要另行处理。
