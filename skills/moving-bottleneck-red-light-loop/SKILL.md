# 移动瓶颈红灯闭环

## R — 原文 (Reading)

> “红绿灯表明该工位运行得是否顺畅无碍……一次次去锁定那些故障点。”
>
> — 沃尔特·艾萨克森，第46章“弗里蒙特工厂地狱”

## I — 方法论骨架 (Interpretation)

流程的总产出通常被当前最慢、最不稳定或等待最多的一个环节限制。先把端到端流转画出来，用等待量、失败率、周期时间或在制品为各环节显示状态，再只选择对总吞吐影响最大的“红灯”。负责人必须观察一次真实工作，而不是只听汇报。每轮只改变一个主要变量并复测总吞吐；原瓶颈解除后，下一处限制会出现，循环随之移动。

## A1 — 书中的应用 (Past Application)

### 案例 1：Model 3 装配线

- **问题**：周产量远低于 5,000 辆目标，多个工位同时报告问题。
- **方法论的使用**：生产状态屏和现场红灯显示阻塞点，马斯克逐工位观察传感器、机械臂和装配动作。
- **结论**：部分问题来自错误默认参数、无意义动作和过度敏感传感器。
- **结果**：机械臂工序被压缩一半，配合去自动化和临时产线最终达到目标。

### 案例 2：太阳能屋顶安装

- **问题**：安装成本持续高于收入，宏观目标无法解释具体亏损。
- **方法论的使用**：负责人到屋顶核对施工动作和每单成本。
- **结论**：问题不是一句“团队不够努力”，而是具体工序、材料与安装效率没有形成可盈利闭环。
- **结果**：该业务仍未达到规模目标，成为“找到红灯后仍需正确方案”的反例。

## A2 — 触发场景 (Future Trigger)

### 适用情境

1. 订单、内容、代码、审批或客服流程不断积压，但各团队都认为自己不是问题。
2. 团队同时提出很多优化项，资源不足以全部处理。
3. 局部指标改善了，总周期或最终交付量却没有变化。
4. 管理者只看到周报，无法解释真实等待和返工。

### 语言信号

- “到底哪个环节拖后腿？”
- “大家都很忙，为什么还是交付不出来？”
- “帮我找到当前瓶颈 / find the bottleneck。”
- “该先优化哪一步？”

### 与相邻 Skill 的区分

- 与 `design-production-responsibility-loop` 的区别：本 Skill 找当前吞吐瓶颈；后者重新安排谁长期承担下游结果。
- 与 `surge-mode-governor` 的区别：本 Skill 诊断和迭代流程；后者决定是否临时集中资源。
- 与 `open-loop-feedback-recovery` 的区别：本 Skill 假设数据入口存在；后者处理反馈被权力或情绪切断。

## E — 可执行步骤 (Execution)

1. **定义端到端结果**
   - 写明入口、出口、统计周期和唯一主结果，例如“每周通过验收的交付数”。
   - 完成标准：结果可计数，且不是某个局部团队的忙碌指标。

2. **画出流转与状态灯**
   - 列出每个环节的输入量、输出量、等待量、周期时间、返工率和故障率。
   - 用红/黄/绿或排序标出对总吞吐影响最大的环节。
   - 完成标准：选出一个主瓶颈，并能说明它如何限制最终结果。
   - 判停条件：若没有可靠数据，先采样一轮真实流转，不得凭印象宣布瓶颈。

3. **来到红灯前**
   - 让决策者与实际操作者共同观察至少一个完整实例。
   - 记录等待、重复动作、无用要求、信息丢失和返工原因。
   - 完成标准：形成可验证的瓶颈机制，而不是“人员不努力”等标签。

4. **单变量试改**
   - 每轮优先删除或改变一个主要限制，保留回退办法。
   - 完成标准：试改后重新测量总吞吐、质量和安全指标。
   - 停止条件：质量、安全、合规或不可逆损失超过预设底线，立即回退。

5. **确认瓶颈是否移动**
   - 如果总吞吐未改善，推翻原假设；如果改善，重新排序状态灯。
   - 完成标准：记录“改了什么、总结果变化多少、下一红灯在哪里”。

## 复盘方式

- 每轮只回答四个问题：原瓶颈假设是什么、现场证据是什么、总吞吐变化多少、瓶颈移到哪里。
- 连续三轮没有改善时，停止局部调参，回到流程边界和结果定义。
- 每周检查是否有人通过隐藏积压、牺牲质量或加班来让状态灯暂时变绿。

## B — 边界 (Boundary)

- 安全、医疗、法律或生产事故仍在处置时，先执行应急程序。
- 没有稳定输入输出的探索性创作，不要伪造精确状态灯。
- 不能因领导者到现场就绕过专业验证、质量和安全负责人。
- 第46章显示产量狂飙伴随更高工伤与捷径；吞吐指标必须与安全、质量并列。
- “红灯”是系统限制，不等于找一个人问责。
