# 鱼骨图主要因验证工作坊

## R — 原文 (Reading)

> 鱼骨图是一个非定量的工具，可以帮助我们找出引起问题潜在的根本原因。
>
> — 《鱼骨图分析法培训》Slide 6, lines 53-60

> “主要因”是对策的内容可以用眼和数据确认的。
>
> — 《鱼骨图分析法培训》Slide 17, lines 140-145

> 每个为什么的问题和答案间必须有必然关系。
>
> — 《5个为什么分析与鱼骨图分析讲义》转换文本 lines 328-336

> 找原因，非找借口、理由；根据数据、事实，而非猜测、假设。
>
> — 《5个为什么分析与鱼骨图分析讲义》转换文本 lines 416-424

## I — 方法论骨架 (Interpretation)

鱼骨图不是“找人背锅”的图，而是把一个可观察异常拆成候选原因、分类、深挖和证据门。它特别适合团队共同面对反复发生的问题，因为每个人都能贡献不同视角。

好的鱼骨会先把鱼头写成可观察结果，再用 6M/5M1E 或业务自定义分类收集原因。所有原因都要尽量写成行为、条件、流程或资源，而不是人格判断。

5Why 是鱼骨里的深挖动作，不是机械问满五次。每一层“为什么”都要能用“因此”倒读回上一层，不能跳步；遇到多个原因时要分叉，而不是把多因问题压成一条漂亮链。

最后不能凭声音大小决定主要因。主要因必须能被现场、数据、记录或实验验证，并且能导向下一步对策。进入 8D 场景时，还要追问“为什么发生”和“为什么没被发现”，把系统漏洞也纳入候选原因。

## A1 — 书中的应用 (Past Application)

### 案例 1: 刹车导管长度不良

- **问题**: 刹车导管出现长度不良。
- **方法论的使用**: 从尺寸混乱、工件不固定、夹紧力不够、气压过低逐层追问，并区分事实和推定。
- **结论**: 深层原因指向汽缸漏气等可观察因素。
- **结果**: 主要因不再停留在“员工注意不足”，而是进入可检查设备条件。

### 案例 2: 毛刺流向后工程

- **问题**: 毛刺不良流向后工程。
- **方法论的使用**: 从不知道、不检查、没有时间、作业不适应等路径追问。
- **结论**: 训练时间短、检查时间不足等条件性原因浮现。
- **结果**: 对策可转向培训、流程和时间安排，而不是单纯责备作业者。

### 案例 3: 迟到与滑倒示例的 5Why 护栏

- **问题**: 资料用迟到、滑倒等示例展示多层“为什么”，同时警告问题与答案之间必须有必然关系。
- **方法论的使用**: 每一层原因都要基于事实、现场、现物和现实，遇到多个可能原因时分支追问。
- **结论**: “问五次”不是目标，找到可验证、可行动的系统原因才是目标。
- **结果**: 讨论从借口和猜测转向可检查的条件、流程和资源。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 质量缺陷、客户投诉、服务延误、交付异常或运营故障反复出现。
2. 团队各执一词，需要把可能原因展开到一张图上。
3. 管理者想开根因会，但担心会议变成指责。
4. 已经有一些现象和数据，但还没有主要因和验证计划。
5. 团队正在做 5Why，但每层原因跳跃、无证据或停在人格判断上。

### 语言信号

- “帮我开一个鱼骨图分析”
- “这个问题为什么反复发生？”
- “找主要因，不要甩锅”
- “root cause / fishbone / 6M / 5M1E”
- “5Why 问到哪里才算停？”
- “这条原因链有没有跳步？”

### 与相邻 skill 的区分

- 与 `problem-analysis-tool-router` 的区别: 路由器判断是否该用鱼骨；本 skill 具体跑鱼骨工作坊。
- 与 `firefighting-to-standard-improvement-loop` 的区别: 鱼骨/5Why 找主要因和漏检点；PDCA/8D 标准化 skill 负责临时措施、永久纠正和复发预防。

## E — 可执行步骤 (Execution)

1. **写鱼头**
   - 完成标准: 鱼头是可观察结果，包含对象、异常、时间/范围和衡量指标。

2. **选择鱼骨类型与分类**
   - 完成标准: 选择原因型、对策型或问题整理型；默认用 6M/5M1E，必要时改为业务分类。

3. **发散候选原因**
   - 完成标准: 会议中禁止批评，完整记录所有原因；人的原因改写为行为、流程、资源或训练条件。

4. **深挖原因链**
   - 完成标准: 对关键原因连续追问为什么，标注事实、推定和待验证；用“因此”倒读相邻两层，确认没有跳步。
   - 判停条件: 如果一层原因只能靠猜测或人格判断支撑，退回现场、数据、记录或样本访谈。

5. **圈定主要因**
   - 完成标准: 每个主要因都能用现场观察、数据、记录或小实验确认。
   - 判停条件: 如果主要因无法验证，只能保留为假设，不得进入对策。

6. **检查漏检点和系统漏洞**
   - 完成标准: 对每个主要因补问“为什么发生”和“为什么未被发现/未被阻止”。
   - 判停条件: 如果问题已经影响客户、安全或合规，转正式 8D/事故流程，不能停在工作坊结论。

7. **形成验证/对策交接**
   - 完成标准: 输出主要因清单、验证方法、漏检点、负责人、截止时间和预期影响指标；验证后交接到 `firefighting-to-standard-improvement-loop`。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 问题没有可观察结果，只有情绪、立场或抽象抱怨。
- 问题入口还没有现状、目标/标准、差距和证据来源，先做 `problem-definition-r1-r2-diagnostic-tree`。
- 团队目的只是追责，不愿区分事实和推定。
- 高风险安全、法律、医疗事故需正式调查流程，不能用普通工作坊替代。

### 作者在书中警告的失败模式

- 头脑风暴时即时批评，导致原因池变窄。
- 把“没有干劲”“注意不足”等态度词当成可行动原因。
- 主要因不能用眼和数据确认。
- 机械问满五次，但层与层之间没有必然关系。
- 只问“为什么发生”，不问“为什么没有发现/阻止”。

### 作者的盲点 / 时代局限

- PPT 以质量管理场景为主；用于内容、销售、教育等业务时，分类要按场景重写，不要机械套 6M。

### 容易混淆的邻近方法论

- 5Why 可作为鱼骨的深挖动作；单条因果链清晰时可先用 5Why，多视角候选原因多时应先画鱼骨。
- 5W2H 用于执行澄清，不等于根因分析。
- 8D/PDCA 用于纠正和防再发，不能替代主要因验证。
